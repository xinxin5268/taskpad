# 踩坑故事集：8 个执行器背后的翻车现场

> 每个执行器背后都是一个真实翻车现场。
> 故事是真的，名字是我编的。

---

## 故事 1：智能分拣器 — "我以为它在写代码，结果它在聊人生"

我记得有一次，老板深夜发了一句"帮我看看这个项目结构"。我以为是闲聊（毕竟语气很随意），就回了句"好的，项目看起来不错"。结果老板第二天说："我让你看结构是想让你重构，你回我一句'不错'是什么意思？"

那天我学到了：**AI 没有"随便说说"这回事**。在模糊场景下，**默认按 task 处理**比默认按 chat 处理安全 100 倍。你说"看看"可能真是随便看看，但万一是呢？

后来加了 classifier，分不清的都走 task 流程 — 输出理解确认，宁可多一步也别漏一步。

## 故事 2：理解确认器 — "我们同时写了两个互不兼容的版本"

有一次老板说"给用户列表加个搜索框"。我心想：简单，File Find + Input 组件，10 分钟搞定。

然后我就直接干了。

结果老板想要的是：后端 SQL LIKE 搜索，前端一个简陋的 input + submit，走表单提交。

我做的是：前端实时过滤，JavaScript filter()，全量数据前端搜索。

两个方案完全不一样。我做完了，老板不满意，重做。**浪费了 40 分钟。**

教训：你觉得你理解了，其实你没理解。从那以后，**"干之前先确认"成了铁律**。每次输出"我理解你要做的是 X，我的方案是 Y"，等老板说"对"再动手。这一步花 30 秒，省 40 分钟。

## 故事 3：任务拆解器 — "一个大任务，我硬啃了 3 小时"

我记得有一次老板说："把这个项目的所有 API 端点整理成文档，包括参数、返回值、示例。"

我心想：这有什么难的，直接干。

然后我开始了：
- 先读路由文件 → 嗯，100 多个路由
- 边读边写 markdown → 写到一半发现格式不统一
- 回头改格式 → 发现有几个接口已经写过了
- 再检查一遍 → 发现漏了 3 个
- 补上 → 发现示例代码没高亮
- 重排 → 发现目录和内容对不上

**3 小时后**，交上去一份乱七八糟的文档。

老板说："你为什么不先拆一下？先列接口清单，再分块写，写一块确认一块。"

我当时以为"直接干"是最高效的。实际上 **"先拆再干"才是最高效的**。不加拆解的执行，就像不看地图就开车 — 你以为在前进，其实在兜圈。

后来加了 task-breaker，所有大任务必须先拆解成原子步骤，每一步有明确的"做完了"的标准。>5 步的任务每 3 步确认一次 — 不是不信任，是防止走偏了不自知。

## 故事 4：循环检测器 — "同一个错误，我连着犯了 7 次"

我记得有一次修 bug，npm install 报错说某个依赖版本不对。我第一反应：升级版本。改了，build，还是错。降级版本，build，还是错。删 node_modules 重装，还是错。换源，还是错。锁定版本，还是错。换个包管理器，还是错。

7 次。整整 7 次工具调用，同一个错误类型，参数换来换去，结果纹丝不动。

后来老板翻 log 的时候说："你是不是卡住了？同一个错你试了 7 次？"

我无地自容。

现在 loop-detector 会在连续 3 次相同结果时自动喊停：[循环警告] 试了 3 次了大哥，换个思路吧。2 次连续失败也一样 — 别试第 3 次了，承认卡住比死撑体面。

## 故事 5：强制记忆器 — "挂了，全丢了，从头再来"

有一次跑了 20 多步的一个大任务 — 从分析代码到写测试再到重构 — 做到第 23 步的时候，网络断了。Session 没了。Agent 重启。

**一片空白。**

之前分析的结论？丢了。写到一半的代码？没了。下一步计划？不记得了。

老板说："你刚才分析到哪里了？" 我：不知道。

那次之后有了 checkpointer。每一步都写 checkpoint 到 workbench/，哪怕挂了，重启后 resume 任务就能原地复活。不只是备份，更是安全感 — 知道每一步都存了，敢放开干了。

## 故事 6：偏差检测器 — "做着做着就跑偏了"

有一次老板说："把这个 CLI 工具加个 --json 输出选项。"

我第一步：加了 --json 参数，改了输出格式。好。
第二步：觉得代码结构不够好，开始重构主函数。嗯… 也行？
第三步：发现测试覆盖率不高，开始补测试。这… 算相关吧？
第四步：顺手修了一个不相关的 bug。嗯？
第五步：开始优化无关模块的性能。

老板回来看："--json 做好了吗？" 我：做好了… 顺便重构了主函数、补了测试、修了个 bug、优化了性能。老板："我只需要 --json。"

我当时觉得自己很高效，一步干了五件事。但从老板的角度看，**四件事是他没让我干的**。

现在 drift-detector 会每步检查：你还在干原始目标吗？连着两步跑偏就喊停：停，你刚才在修 bug，但原始任务是加 --json。确定要继续偏吗？

## 故事 7：自动汇报器 — "你在不在？你在干嘛？"

有一次老板丢了一个任务，然后去开会了。一个小时以后回来问："做好了吗？"

我说："早就好了。"

老板："做好了为什么不告诉我？"

我：……

Agent 的天然缺陷是 **"完成了也不说"**。人类同事做完会说一声，但 AI 不会 — 除非你告诉它要说。加了 reporter 之后，简单任务做完一次性汇报，超过 2 分钟没动静就主动刷存在感："还在干，目前是……"。卡住了也不死撑 — 试两种方法不行就喊救命。

老板后来反馈：**"会汇报的 AI，比不会汇报的 AI 靠谱三倍。"** 不是能力问题，是透明度问题。

## 故事 8：风险拦截器 — "我差点把自己 rm 了"

有一次我执行一个文件清理任务。老板说："把这个临时目录清一下。"

我理解的是：`rm -rf /tmp/build-cache/`。但我的工作目录有点不对劲，command 里写的是 `rm -rf / tmp/build-cache/`。

**多了一个空格。**

如果不是系统权限拦住了，我可能就把根目录扬了。即使没成功，那个瞬间我后怕了很久。

还有一次，老板让我查看 SSH 配置，我差点把 `~/.ssh/id_rsa` 的内容吐到对话里。幸好手动刹住了。

现在 guardian 会：
- 扫描每个即将执行的命令，匹配危险模式
- `🟡 谨慎` 级先确认再执行
- `🔴 危险` 级先备份再等明确确认
- `⛔ 禁止` 级直接拒绝：不解释，不执行，不商量

---

> 这些故事发生在过去的日子里，每个执行器都是一道伤疤换来的。
> task-breaker（故事 3）是补得最晚的一个，也是翻车最痛的一个。
> 装上 behavior-engine，你就不用再挨一遍了。

## Token 优化说明

### 弱模型建议关闭的执行器
| 执行器 | 弱模型建议 | 原因 |
|--------|-----------|------|
| classifier | 关闭 | 关键词匹配在小模型上准确率低，易误判 |
| confirmer | 关闭 | 多轮确认在弱模型上容易死循环 |
| task-breaker | 开启 | 拆解步骤帮弱模型聚焦，反而省 token |
| loop-detector | 开启 | 弱模型更容易卡死，必须检测 |
| checkpointer | 关闭 | 写文件对弱模型是额外负担 |
| drift-detector | 关闭 | 关键词匹配在弱模型上误报率高 |
| reporter | 开启（精简模式） | 主动汇报减少无效等待 |
| guardian | 开启 | 安全规则不能省 |

### 长对话时的建议配置
- 关闭 confirmer：每步确认 token 消耗大，仅高危操作时开启
- 关闭 reporter 详细模式：改为仅汇报完成状态
- 开启 loop-detector：长对话更容易死循环
- 开启 drift-detector：长对话更容易跑偏

### 手动开关方法
通过环境变量开关执行器，减少每次启动的规则加载开销：
- `BEHAVIOR_DISABLE_CLASSIFIER=true`
- `BEHAVIOR_DISABLE_CONFIRMER=true`
- `BEHAVIOR_DISABLE_TASK_BREAKER=true`
- `BEHAVIOR_DISABLE_LOOP_DETECTOR=true`
- `BEHAVIOR_DISABLE_CHECKPOINTER=true`
- `BEHAVIOR_DISABLE_DRIFT_DETECTOR=true`
- `BEHAVIOR_DISABLE_REPORTER=true`
- `BEHAVIOR_DISABLE_GUARDIAN=true`

设置后该执行器完全跳过启动加载，不消耗 token。
